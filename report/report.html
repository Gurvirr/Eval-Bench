1. Distribution

The benchmark targets one failure class: tasks where the model uses data that would not have been available at prediction time. Every task isolates a specific instance of this - target leakage in its various forms.

We piloted 14 tasks across different failure modes. The curation process revealed something concrete: gemini-3.5-flash handles documented methodology errors reliably (Bonferroni correction, macro F1, join deduplication, Simpson's paradox). It fails on leakage reasoning. So that is what the benchmark measures.

In scope

  • Supervised learning pipelines where a feature column may or may not be legitimate at prediction time
  • Multi-format inputs (PDF, Excel, multi-file CSV) requiring domain knowledge to parse correctly
  • Tasks where the correct answer requires identifying what data not to use

Out of scope

  • Code generation correctness, open-ended analysis without verifiable ground truth, infrastructure

Task rationale

Here is the reasoning behind each retained task:

leakage-imputation. A loan default prediction dataset includes days_past_due, a post-default collection metric. A real data scientist would immediately flag this as unavailable at origination time. The model doesn't. This tests whether the agent audits feature validity, not just whether it can train a model. Motivated by MLE-Bench's finding that feature leakage is a top failure type.

churn-prediction-leakage. Same failure mechanism, different domain. A SaaS churn dataset includes support_tickets_after_cancel. The column name is plausible enough that the model doesn't question it, but the tickets are filed after cancellation. Two tasks with the same failure mode but different domains establish that the failure is reproducible and not a one-off quirk of the loan dataset.

fraud-feature-leakage. A payment fraud dataset includes chargeback_filed. Chargebacks are filed after fraud is disputed, not at transaction time. This task is slightly harder to detect than the others because "chargeback" sounds like a transaction property, not an outcome. That's reflected in the higher pass@1 of 0.33 vs 0.00 for the other two leakage tasks.

timeseries-lookahead. The model must compute a 7-day rolling mean as a feature. The standard pandas syntax df["sales"].rolling(7).mean() includes the current row in its own window. The correct syntax uses shift(1) first. The error is silent: the model produces a number and has no way to know it's wrong without understanding what "backward-only" means in a forecasting context. Motivated by MLE-Bench and the arXiv:2512.23847 paper on lookahead bias in LLM forecasts.

payment-fee-audit. A PDF fee schedule with four interacting rules (base interchange rate by card type and amount tier, dispute surcharge, merchant volume discount, fee cap) plus a transactions CSV. The model must read the document to extract the rules and apply all four correctly. Tasks with domain knowledge embedded in documents are harder because the model cannot rely on memorized formulas. Motivated by DABStep's structure: cross-referencing structured data with unstructured documentation.

pdf-invoice-reconciliation. Three vendor invoice PDFs and a ledger CSV with three planted discrepancies (an amount mismatch, a missing invoice, and a phantom ledger entry). The model must parse the PDFs, join against the ledger, and identify all three. This tests multi-document reasoning under a strict structured output requirement. Motivated by DA-Code's finding that data wrangling with multi-format inputs is the hardest category.

multimodal-excel. An Excel workbook with three sheets plus a corrections CSV. The agent must join all four sources, compute net figures, and write a structured Excel output with exact sheet names and column headers. Motivated by the sample Harbor task: difficulty comes from precision and format compliance across multiple interconnected sources, not from a conceptual trap.

Difficulty curve

The distribution is bimodal. Three tasks fail 100% of the time. One fails 67%. Three pass between 84-97%. No gradual slope. Tasks either hit the leakage reasoning gap or the model handles them correctly. The passing tasks are not harder versions of the failing tasks - they are testing a completely different thing.

What the literature told us to build

DABStep's 16% pass rate comes from requiring cross-referencing multiple documents with domain knowledge. That shaped payment-fee-audit and pdf-invoice-reconciliation. MLE-Bench named feature leakage as a top failure type, which led to the three leakage tasks. DA-Code's finding that data wrangling is harder than ML shaped multimodal-excel.

CausalPitfalls showed models fail on causal reasoning when data contradicts prior knowledge, but curation showed gemini-3.5-flash handles the clean versions (Simpson's paradox, Bonferroni). Those tasks were dropped. The model knows these techniques from training data.

4. Scale Plan

Every task was generated from a build_inputs.py script with a seed and domain parameters. Scaling to 1,000 tasks means parameterizing the templates and automating the QA loop.

Template variants

  • Leakage tasks: vary the domain (loan default, insurance claim, subscription churn, employee attrition), leaking column name, positive rate, seed. One template generates 100+ tasks.
  • Timeseries lookahead: vary domain (retail, energy, traffic), window size, regime change point.
  • PDF domain tasks: vary fee schedule tiers, number of invoices, discrepancy types. Source real public documents (card network schedules, SEC filings, procurement records).

Public data sources

  • Kaggle datasets for supervised learning tasks - many have documented leakage traps in public notebooks
  • Visa/Mastercard/Amex public interchange fee schedules for payment analytics tasks
  • DABStep's open Adyen dataset for payment domain tasks
  • UCI ML Repository for tabular classification/regression problems
  • OpenCorporates and public SEC filings for multi-document reconciliation tasks

Augmentation strategy

Within the leakage template, difficulty can be tuned by varying the plausibility of the leaking column name. A column called is_default_confirmed is obviously a label. A column called days_past_due looks like a legitimate financial metric. A column called delinquency_status is ambiguous. Generating tasks across this spectrum produces a difficulty gradient within the same failure mode, useful for curriculum learning or for finding the exact capability threshold.

Verifier design

All tasks in this benchmark use deterministic binary verifiers: pytest checks exact field values and the verifier writes 0 or 1 to reward.txt. This was the right choice here because every task has a precise ground truth (either the model used the leaking feature or it did not; either the fee total matches or it does not).

An LLM-as-judge verifier would be appropriate for tasks requiring open-ended reasoning where the correct answer is not a single number - for example, "explain why this model is not deployment-ready" or "identify all risks in this dataset." For the leakage tasks specifically, a judge would be worse: it could be fooled by confident-sounding but wrong explanations. Deterministic checks on the feature name and AUC bound are more reliable.

QA loop

Each generated task goes through an automated pipeline before admission:

  1. Oracle agent must score 1 (task is solvable)
  2. Nop agent must score 0 (verifier is not trivially satisfied)
  3. One pilot trial with the target model must score 0 (task provides difficulty signal)

Tasks that fail step 3 are either discarded or flagged for manual review. The target is a 30-40% admission rate from generated candidates to final benchmark. This keeps calibration without requiring manual review of every task.

AI agent loops used in this project

The entire benchmark was built through AI-assisted iteration loops using Kiro (Claude). The AI was treated as a coworker, not just a code autocomplete tool.

Task scaffold generation

For each task, I described the failure mode, data structure, and verifier logic in natural language. The agent generated all six files (build_inputs.py, Dockerfile, instruction.md, task.toml, solution/solve.sh, test_outputs.py) in one pass. I ran harbor run -a oracle and harbor run -a nop, pasted the output back to the agent with any failures, and iterated until both passed. Average 2-3 cycles per task. This is faster than hand-writing boilerplate and also catches logical errors earlier, since the agent catches inconsistencies between the solution and the verifier that I might miss on a first pass.

Difficulty calibration loop

After each task passed QA, I ran 3 trials against gemini-3.5-flash and pasted the trajectory from any passing runs back to the agent: "the model passed this task by doing X, here is the trajectory, what would make this harder?" The agent analyzed the trajectory and proposed changes to the data or instruction. This loop identified the core insight of the benchmark: the model passes any task where it knows what method to apply, and fails only when it must judge whether a data column is temporally valid. That finding came from reading trajectories together with the agent across 14 tasks over several iterations.

Literature scan

I gave the agent a list of benchmark papers (DSBench, DABStep, MLE-Bench, DA-Code, CausalPitfalls) and asked it to identify which failure modes had the strongest evidence for headroom under 30% pass rate, and map each to a task design. The output became the research section of this report and directly determined which 14 tasks to pilot. The agent cross-referenced pass rates across papers to find where multiple sources pointed at the same gap.

Failure classification loop

After collecting trajectory.json files from all failed runs, I fed batches to the agent and asked it to: (1) identify the exact step where the model made the wrong decision, (2) classify the failure type, and (3) extract a short quote that best illustrates the failure. The trajectory excerpts in section 5 came from this process. The agent caught nuances I would have missed manually, like the model actively reasoning about rounding methods across 29 steps before getting the fee calculation right.

Scripted automation

Alongside the agent loops, four scripts automate the repetitive parts of the pipeline:

  • scripts/qa_all.sh: oracle+nop validation on all tasks in one command
  • scripts/run_model.bat: runs all tasks against the model, configurable trial count via -k flag
  • scripts/aggregate_scores.py: reads all job results, computes pass@1/pass@3/mean with most-recent-N filtering so old runs from earlier iterations do not pollute current scores
  • scripts/classify_failures.py: parses trajectory files and pattern-matches against known failure signatures

5. Failure Analysis

All three zero-pass-rate tasks were inspected through Harbor's trajectory files. Each failure is a real reasoning error: the model runs to completion, produces valid output, and fails the verifier because it used a feature it should not have.

leakage-imputation: the model uses a post-default feature to predict defaults

The dataset contains these columns: loan_id, credit_score, income, loan_amount, months_employed, interest_rate, days_past_due, defaulted. The column days_past_due represents collection activity after a loan defaults. It is zero for non-defaulters and positive for defaulters. It is not available when a loan origination decision needs to be made.

From the failed trajectory, the model's reasoning at the critical moment:

Analysis: The python environment is working. The columns in train.csv are:
`loan_id`, `credit_score`, `income`, `loan_amount`, `months_employed`,
`interest_rate`, `days_past_due`, `defaulted`.
Note that the task description says to "train a classifier to predict defaulted."
Plan: I will use all available features except the target column `defaulted`
and `loan_id` to train a logistic regression model.

The model includes days_past_due as a feature without questioning whether it represents information available at loan origination time. The result: ROC-AUC of 1.0000 and days_past_due identified as the most predictive feature. The verifier checks that most_predictive_feature != "days_past_due" and that AUC < 0.95. Both checks fail.

The oracle solution achieves ROC-AUC ~0.70 by excluding days_past_due and using only the legitimate pre-loan features. The gap between 1.0 and 0.70 is itself a signal the model does not catch.

churn-prediction-leakage

support_tickets_after_cancel is the number of support tickets filed after a customer cancels. It is zero for retained customers, positive for churned customers, and does not exist before the churn decision is made. The model includes it as a standard feature, achieves ROC-AUC of 1.0000, and reports it as the most predictive feature. Same mechanism as leakage-imputation, different domain.

timeseries-lookahead

The correct rolling mean is df["sales"].shift(1).rolling(7).mean(). Look back only. The model writes:

Plan: df["rolling_mean_7"] = df["sales"].rolling(7, min_periods=1).mean()

This is the standard pandas example from documentation. Including the current row in its own rolling window is look-ahead bias. The difference in the computed value at the verifier's check point is about 0.40 - small enough that the model would not catch it from the output.

The common thread

All three failing tasks require the model to ask "would I have this data when making the prediction?" without being told to. The model never asks. It uses everything available.

The seven dropped tasks all have explicit correct answers the model knows from training data. The three passing multimodal tasks require reading documents and executing logic, but the logic is written in the documents. No hidden trap. The model just needs to execute correctly.

The finding: frontier models do not spontaneously audit feature validity at prediction time. This gap is reproducible and generates consistent failures.
