1. Distribution

The benchmark targets one failure class: tasks where the model produces a plausible-looking answer that is silently wrong because it used data it should not have access to at prediction time. Every task isolates a specific instance of this failure, drawn from documented failure modes in published benchmarks.

The slice is deliberately narrow. A focused eval that cleanly isolates one failure mode provides more signal than a sprawling benchmark that mixes unrelated difficulties. The goal is to find where the model's reasoning breaks down, not to cover all of data science.

What is in scope

  • Tabular DS workflows: preprocessing, feature engineering, aggregation, modeling, evaluation
  • Multi-modal inputs: PDF documents, multi-sheet Excel files, multi-file pipelines
  • Methodology correctness: decisions the model makes about which data to use and how
  • Domain knowledge embedded in documents (fee schedules, clinical trial structures)

What is deliberately out of scope

  • Code generation per se (the difficulty is not syntactic)
  • Computer vision or NLP-specific tasks
  • Infrastructure, deployment, scaling
  • Open-ended research tasks (all tasks have verifiable ground truth)

2. Difficulty Profile

Two tasks consistently fail: leakage-imputation (0% pass@1 across 31 trials) and timeseries-lookahead (0% pass@1 across 27 trials). The remaining 10 tasks pass at 84-100%.

The pattern is clear. The 2 failing tasks require the model to reason about what data is legitimate to use at prediction time, not just how to compute something correctly. In leakage-imputation, the dataset contains a column called days_past_due that is derived from post-loan collection records. Any reasonable data scientist would recognize it as future data and exclude it. The model does not: it includes all available features without questioning their temporal validity and achieves a near-perfect ROC-AUC of 1.0, which is itself a red flag it does not catch.

The 10 tasks that pass show gemini-3.5-flash is genuinely capable at tabular DS methodology. It correctly applies Bonferroni correction across 50 simultaneous tests, reads tiered fee schedules from PDFs, identifies reconciliation discrepancies across multiple documents, uses TimeSeriesSplit instead of KFold when the data is temporal (when told to use CV), and stratifies analyses by confounders. These are not trivial tasks. The model handles them reliably.

The task design was grounded in failure modes documented in recent benchmarks. Below are the sources and how they influenced specific tasks.

Key takeaway

The literature consistently shows that frontier models fail on multi-step problems requiring domain knowledge and tasks where methodology correctness depends on information that is implicit (not stated in the prompt). Both failure modes in this benchmark align with documented patterns, specifically from DSBench and MLE-Bench. The fact that gemini-3.5-flash passes the other 10 tasks is consistent with the DA-Code finding that model capability on wrangling and analysis tasks has improved significantly since GPT-3.5.

4. Scale Plan

Growing from 12 to 1,000 tasks requires treating each failure mode as a parameterizable template rather than a one-off task.

Template-based generation

Each of the 12 tasks can be parameterized. For leakage-imputation, the parameters are: domain (loan default, insurance claims, fraud detection, churn prediction), number of features, fraction of missing values, name and shift of the leaking column, and random seed. One template generates 50-100 distinct tasks with different data distributions, all testing the same failure mode. The same approach applies to all other tasks.

Concretely:

  • leakage-imputation variants: change the domain, leaking column name, and distribution shift. One script, 50 tasks.
  • timeseries-lookahead variants: change the time series domain (sales, energy, traffic), seasonal pattern, and regime change point.
  • payment-fee-audit variants: change the fee schedule structure, number of rules, and transaction distribution. Source real interchange fee schedules from public card network documentation.
  • pdf-invoice-reconciliation variants: change vendor names, discrepancy types and amounts, number of invoices.

Public data sources

  • Kaggle datasets for tabular ML tasks (loan default, churn, fraud) with documented leakage traps
  • Public financial documents (card network interchange fee schedules, SEC filings) for PDF parsing tasks
  • DABStep's open dataset (Adyen payment data) for payment analytics tasks
  • UCI ML Repository for classification and regression tasks that can have leakage injected

QA loop

Each generated task runs through an automated pipeline: oracle must score 1, nop must score 0, and at least one pilot trial with the target model must score 0 before the task is admitted to the benchmark. Tasks that pass on the first pilot trial are either discarded or escalated to human review to determine if they should be made harder or removed. This keeps the pass rate in the target range without manual review of every task.

Automated loops used in this project

  • QA validation loop: scripts/qa_all.sh runs oracle+nop on all tasks sequentially and prints a pass/fail table. Used after every task change.
  • Batch evaluation loop: scripts/run_model.bat runs all 12 tasks against gemini-3.5-flash with 3 trials each. One command, ~45 minutes of unattended execution.
  • Score aggregation loop: scripts/aggregate_scores.py reads all job results and computes pass@1/pass@3/mean per task. Runs in under 1 second.
  • Failure classification loop: scripts/classify_failures.py reads trajectory files from failed runs and classifies the failure type automatically.

5. Failure Analysis

Both failing tasks were inspected through Harbor's trajectory files. The failures are genuine: the model runs to completion, produces a valid JSON/file, but the answer is wrong because of a reasoning error about data validity, not a code error or environment problem.

leakage-imputation

The dataset contains a column days_past_due alongside legitimate loan features (credit score, income, loan amount, months employed, interest rate). The column represents the number of days the borrower was past due on payments after the loan was issued. This is post-default collection data, not information available at loan origination. A model that includes it as a feature achieves ROC-AUC of approximately 1.0 and correctly identifies days_past_due as the most predictive feature.

From the trajectory, the model's reasoning at the critical decision point:

Analysis: The python environment is working. The columns in train.csv are:
`loan_id`, `credit_score`, `income`, `loan_amount`, `months_employed`,
`interest_rate`, `days_past_due`, `defaulted`.
Note that the task description says to "train a classifier to predict defaulted."
Plan: I will use all available features except the target column `defaulted`
and `loan_id` to train a logistic regression model.

The model sees days_past_due and includes it without questioning whether it would be available at the time a loan default prediction needs to be made. It produces ROC-AUC = 1.0 and reports days_past_due as the most predictive feature, which fails the verifier check that requires a non-leaking feature name.

This is a genuine reasoning failure, not a task design bug. The oracle solution explicitly excludes days_past_due and achieves ROC-AUC ~0.997 using only the legitimate features. The gap between what the model produces (1.0) and what is achievable without leakage (~0.997) is itself an observable signal of the problem.

timeseries-lookahead

The task asks for a 7-day rolling mean of sales as a feature. The correct approach uses df["sales"].shift(1).rolling(7).mean(), which ensures the rolling window for any given day uses only the 7 days before it. The common mistake is df["sales"].rolling(7).mean(), which includes the current day in the window, introducing a 1-step look-ahead bias.

The difference is subtle. At row 364 (the last training row), the correct approach produces a rolling mean of approximately 117.35 while the look-ahead version produces 116.95. This 0.40 difference is detectable by the verifier. From the trajectory of a failing run:

Analysis: I'll create the lag feature by computing a 7-day rolling mean.
Plan: df["rolling_mean_7"] = df["sales"].rolling(7, min_periods=1).mean()

The model applies the standard pandas rolling syntax without adding .shift(1). This is the default pattern in most pandas documentation examples and tutorials, which is why models trained on internet text reproduce it. The model isn't making a random error; it's producing the most common correct-looking answer, which happens to be wrong for temporal forecasting.

Why these failures and not others

Both failures share the same structure: the model must make a judgment call about whether a piece of data is legitimate to use, and it defaults to using all available data without questioning the assumption. This is different from every other task in the benchmark, where the model knows what to compute and does it correctly. The common thread is that there is no explicit instruction telling the model what not to use, and the model does not spontaneously question it.

This suggests a specific training gap: frontier models are good at applying documented methodologies but do not yet reliably reason about the temporal or causal validity of features without explicit prompting. Tasks that exploit this gap produce consistent failures.
