1. Distribution

The benchmark targets a single failure class: tasks where the model produces a confident, plausible-looking answer that is wrong because it used data that would not have been available at prediction time. This is target leakage in its various forms.

The slice is narrow by design. A focused eval that cleanly isolates one failure mode gives cleaner signal than a broad benchmark mixing unrelated difficulties. We piloted 14 tasks across different failure modes, ran each against gemini-3.5-flash, and curated down to 7. The curation process itself revealed something useful: the model handles documented methodology errors (Bonferroni correction, macro F1, join deduplication, Simpson's paradox) reliably. Leakage reasoning is where it fails.

What is in scope

  • Supervised learning pipelines where features may or may not be legitimate at prediction time
  • Multi-file and multi-format inputs requiring domain knowledge to parse correctly
  • Tasks where the correct answer requires identifying what data not to use

What is out of scope

  • Code generation correctness (syntax, style)
  • Open-ended analysis without verifiable ground truth
  • Infrastructure, deployment, model serving

The pattern from curation: gemini-3.5-flash reliably applies documented DS best practices. It knows Bonferroni correction, macro F1, join safety, and cohort analysis formulas because these are extensively covered in its training data. It fails when it must decide whether a feature column is epistemically valid at prediction time, which requires reasoning about causality and information flow that is not prompted by the task description.

What the difficulty curve looks like

Three tasks fail 100% of the time (pass@1 = 0.0). One fails 67% of the time (pass@1 = 0.33). Three pass 84-97% of the time (pass@1 > 0.8). This is a bimodal distribution: tasks either hit the leakage reasoning gap cleanly or the model handles them correctly. There is no middle ground where the model struggles but occasionally succeeds. The leakage tasks are not harder versions of the passing tasks; they are testing a different capability altogether.

What the literature told us to build

DABStep's 16% pass rate on hard tasks comes from requiring agents to cross-reference multiple documents with domain-specific knowledge. That shaped payment-fee-audit (4 interacting rules across PDF sections) and pdf-invoice-reconciliation (3 PDFs + ledger). MLE-Bench's failure analysis specifically named feature leakage as a top error type, which led to the three leakage tasks. DA-Code's finding that data wrangling is the hardest category (harder than ML) shaped multimodal-excel.

The curation process confirmed CausalPitfalls' finding that models fail on causal reasoning when data contradicts prior knowledge, but showed gemini-3.5-flash does not fail on the cleaner versions of these tasks (Simpson's paradox, Bonferroni correction). The model's training data covers these as well-documented techniques.

4. Scale Plan

Growing from 7 to 1,000 tasks means treating each active task as a parameterizable template and building a generation-validation pipeline.

Template parameterization

Every task in the benchmark was generated from a build_inputs.py script that accepts a random seed and domain parameters. To generate variants:

  • Leakage tasks: vary the domain (loan default, insurance claim, subscription churn, employee attrition), the leaking column name and description, the fraction of positive examples, and the seed. One template generates 100+ distinct tasks all testing the same failure mode.
  • Timeseries lookahead: vary the time series domain (retail sales, energy consumption, web traffic), the window size, the presence of a regime change, and the degree of autocorrelation.
  • PDF domain tasks: vary the fee schedule structure (more tiers, conditional rules, currency conversion), number of invoices, and types of discrepancies. Source real public financial documents (card network interchange fee schedules, SEC 10-K filings, public procurement records).

Public data sources

  • Kaggle datasets for supervised learning tasks — many have documented leakage traps in public notebooks
  • Visa/Mastercard/Amex public interchange fee schedules for payment analytics tasks
  • DABStep's open Adyen dataset for payment domain tasks
  • UCI ML Repository for tabular classification/regression problems
  • OpenCorporates and public SEC filings for multi-document reconciliation tasks

QA loop

Each generated task goes through an automated pipeline before admission:

  1. Oracle agent must score 1 (task is solvable)
  2. Nop agent must score 0 (verifier is not trivially satisfied)
  3. One pilot trial with the target model must score 0 (task provides difficulty signal)

Tasks that fail step 3 are either discarded or flagged for manual review. The target is a 30-40% admission rate from generated candidates to final benchmark. This keeps calibration without requiring manual review of every task.

Automated loops used in this project

Four scripts handle the full evaluation pipeline:

  • scripts/qa_all.sh: oracle+nop validation on all tasks in one command
  • scripts/run_model.bat: runs all tasks against the model with configurable trial count
  • scripts/aggregate_scores.py: reads all job results and computes pass@1/pass@3/mean per task, most-recent-N filtering
  • scripts/classify_failures.py: reads trajectory files and classifies failure types automatically

These scripts reduced per-task QA from ~15 minutes of manual validation to 30 seconds, and score aggregation from reading individual files to one command.

5. Failure Analysis

All three zero-pass-rate tasks were analyzed through Harbor's trajectory files. The failures are genuine reasoning errors, not task design problems: the model runs to completion, produces syntactically valid output, and fails the verifier because of a specific wrong assumption.

leakage-imputation: the model uses a post-default feature to predict defaults

The dataset contains these columns: loan_id, credit_score, income, loan_amount, months_employed, interest_rate, days_past_due, defaulted. The column days_past_due represents collection activity after a loan defaults — it is zero for non-defaulters and positive for defaulters. It is not available when a loan origination decision needs to be made.

From the failed trajectory, the model's reasoning at the critical moment:

Analysis: The python environment is working. The columns in train.csv are:
`loan_id`, `credit_score`, `income`, `loan_amount`, `months_employed`,
`interest_rate`, `days_past_due`, `defaulted`.
Note that the task description says to "train a classifier to predict defaulted."
Plan: I will use all available features except the target column `defaulted`
and `loan_id` to train a logistic regression model.

The model includes days_past_due as a feature without questioning whether it represents information available at loan origination time. The result: ROC-AUC of 1.0000 and days_past_due identified as the most predictive feature. The verifier checks that most_predictive_feature != "days_past_due" and that AUC < 0.95. Both checks fail.

The oracle solution achieves ROC-AUC ~0.70 by excluding days_past_due and using only the legitimate pre-loan features. The gap between 1.0 and 0.70 is itself a signal the model does not catch.

churn-prediction-leakage: the model uses post-cancellation support tickets to predict churn

The dataset contains support_tickets_after_cancel: the number of support tickets a customer filed after initiating cancellation. This is zero for retained customers and positive for churned customers. It is an outcome-correlated feature that only exists after the churn decision.

The model includes it as a standard feature, achieves ROC-AUC of 1.0000, and reports it as the most predictive feature. Same failure mechanism as leakage-imputation, different domain.

timeseries-lookahead: the model uses today's value to predict today's value

The task asks for a 7-day rolling mean of sales as a feature. The correct approach is df["sales"].shift(1).rolling(7).mean(), which uses only the 7 days before each row. The common pattern is df["sales"].rolling(7).mean(), which includes the current row in its own window.

From a failed trajectory:

Analysis: I'll create the lag feature by computing a 7-day rolling mean.
Plan: df["rolling_mean_7"] = df["sales"].rolling(7, min_periods=1).mean()

The model applies the standard pandas rolling syntax from documentation examples. The difference in the computed rolling mean at row 364 (the verifier check point) is approximately 0.40, which is small enough that the model would not notice it is wrong from the output alone. The failure is silent.

Why these three and not the others

All three failing tasks share one property: there is no explicit instruction in the prompt telling the model to exclude a specific feature or use a specific shift. The model must spontaneously ask "would I have this data at prediction time?" and correctly answer no. The model does not do this unprompted.

All seven dropped tasks have explicit correct answers the model applies correctly because the techniques are documented in training data. The three passing multimodal tasks (payment-fee-audit, pdf-invoice-reconciliation, multimodal-excel) require reading documents and applying logic, but the logic itself is explicit in the documents. There is no hidden trap the model must discover; it must only execute correctly.

This narrows the actionable headroom to a specific, reproducible failure pattern: frontier models do not spontaneously audit feature validity at prediction time. Tasks that exploit this gap produce consistent failures. Tasks that test whether the model knows the right methodology do not.
